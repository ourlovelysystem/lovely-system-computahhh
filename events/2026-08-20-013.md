# Event 2026-08-20-013

**Time:** 2026-08-20 EDT

## COMMAND

> Computer create an event recohhhrd and run program.

## OBSERVED DEFECT

Live testing demonstrated that the backend countdown balance was burning at the requested 20× rate when progress reached zero, but the browser displayed a radically smaller clock such as `04:17` instead of a roughly 78-minute countdown visibly racing downward.

Captured API observations demonstrated the backend behavior was correct:

- 4724 → 4524 countdown seconds over 10 real seconds.
- 4524 → 4424 over 5 real seconds.
- 4424 → 4364 over 3 real seconds.
- 4364 → 4304 over 3 real seconds.

These are all consistent with a 20× countdown rate.

## CAUSE

Two browser components were writing to the countdown display.

`lovely-system-alert.js` continued to derive the displayed clock from the backward-compatible diagnostic `self_destruct_deadline`, while `lovely-system-countdown-rate.js` rendered the authoritative `countdown_remaining_seconds` balance using `countdown_rate`.

At 20×, the diagnostic wall-clock ETA is approximately one twentieth of the countdown-time balance, so the legacy renderer displayed a few real minutes while the authoritative renderer displayed tens of countdown minutes. The two renderers fought over the same visible clock.

## PROGRAM

Establish one countdown presentation authority. The shared alert client is to render directly from the authoritative countdown balance and rate. The auxiliary countdown-rate renderer is to be removed from the page/workflow so there is no competing writer.

The display remains ordinary `MM:SS` countdown time. At progress zero it visibly runs at 20×; at progress one or greater it runs at 1× without refunding time already consumed.

## STATUS

Event recorded before corrective mutation, per operator command. Corrective program authorized to run.
