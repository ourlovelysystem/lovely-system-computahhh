# Event 192 — Pledge temporary session design

## Purpose

A visitor arriving at Ready presses one doorbell-like button. The system plays a two-tone doorbell, then the selected “Who are you?” challenge track, then a start beep. Recording begins immediately and runs to a fixed hard stop. A visible countdown shows remaining time. A closing beep marks the end. The recording is accepted for upload, transcription, and semantic evaluation regardless of whether the visitor says a name, a description, “UPS,” or something else.

## Session model

Pledge will use two linked but distinct session identifiers:

- **Server session ID:** UUIDv4, created by the session-start API and stored as `session_id` in DynamoDB.
- **Browser-tab token:** a cryptographically random opaque secret returned once to the browser. The browser stores it with `session_id` in `sessionStorage`. DynamoDB stores only its hash.

This is a temporary possession mechanism, not a durable user identity or authentication claim. A later request supplies both values. The API retrieves the record by `session_id`, hashes the presented token, and requires equality with the stored hash.

`sessionStorage` is intentionally tab-scoped and disappears when that tab closes. `localStorage` is not the default because it survives browser restart.

## Initial DynamoDB record

```json
{
  "session_id": "UUIDv4",
  "browser_session_hash": "SHA-256 of opaque token",
  "status": "ready",
  "created_at": 0,
  "updated_at": 0,
  "expires_at": 0,
  "challenge_id": "who-are-you-v1",
  "recording_seconds": 12,
  "events": []
}
```

`expires_at` is an epoch-seconds DynamoDB TTL attribute. Application code must also reject expired sessions because TTL deletion is asynchronous.

## Initial transition model

```text
ready → challenge_playing → recording → submitted → processing → complete
```

The record may hold temporary behavior-driving facts: button press, challenge track, playback completion, start time, recording deadline, receipt ID, transcription status, semantic-validation status, and duplicate-submission guard.

## Proposed first recording limit

**12 seconds.** It is long enough for an answer with personality and short enough to keep the interaction decisively bounded.

## Not implemented by this entry

This documents the proposed design only. No API, DynamoDB table, browser storage, or audio-flow behavior changed.
