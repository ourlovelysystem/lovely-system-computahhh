## Failure

## Cause

The server updates authoritative state atomically, then broadcasts each accepted impact through independent Lambda invocations and WebSocket deliveries. Those deliveries may arrive out of order.

The witness clients accepted every arriving state summary without checking whether it was newer than the state already held. A late-arriving message carrying an older sequence could therefore overwrite a newer sequence and lower the client's visible counters. The client had received the events but regressed its state.

The faulty assumption was:

> **Last delivered equals newest.**

That assumption is false in this transport.

## Remedy

The client state-ingestion rule was changed to be monotonic:

- a state from an older target generation is rejected;
- within the current generation, a state with a lower server sequence is rejected;
- a state with a newer generation is accepted, including the intentional zero state created by target replacement;
- stale-state rejection is written into the machine-readable trace;
- impact identifiers remain independently deduplicated.

The remedy does not reorder the network. It prevents network reordering from moving accepted client state backward.

Teambuilder remedy commit:

- `795ad78fa589824fd092cef3539d30e8588a10b9` — **Prevent witness clients from regressing on reordered state**

After deployment, Witness Mode returned to **READY — 4 / 4 SHARED**.

## Evaluation

This is a useful failure.

The plumbing transported enough information to expose the bug, but transport and convergence are not identical. A client can receive all events and still display regressive state if it treats arrival order as authority. The witness test therefore discovered a real defect in the client convergence contract before a successful movie could be presented as evidence.

The remedy is narrow and principled. It accepts the server sequence as the ordering authority while preserving immediate local rendering. It should now be tested, not celebrated.
