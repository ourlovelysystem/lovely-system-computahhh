# Event 077 — Durable Local and Remote Shot Distinction

**Date:** 2026-08-23  
**System:** Our Lovely System — Computahhh  
**Status:** CURRENT VISUAL RULE SELECTED / FUTURE ALTERNATIVE PRESERVED / LOCAL FEEDBACK PATH REVISED

## Immediate design correction

The shared-gallery program initially placed authoritative shot resolution in AWS.

Under that design, the firing browser could produce recoil, flash, and sound immediately, but it could not draw the crater until AWS returned the resolved impact.

The operator rejected that delay:

> **That is suboptimal and unnecess'ry. A better experience is to show the shot locally without delay and not wait for the server to tell the client what the client already knows because it just told the server. Gaps in remote shot timing will be easily more tolerable than gaps in local shot timing.**

The revised path is:

1. the firing client resolves deviation locally;
2. it immediately displays recoil, sound, flash, and crater;
3. it sends the completed normalized impact to AWS;
4. AWS validates, stores, and broadcasts the event;
5. the firing client ignores the echoed duplicate by shot ID;
6. remote browsers display the impact when received.

AWS remains authoritative for shared history. It is removed from the local feedback loop.

## Aim is not transmitted

The operator asked:

> **Here we are not transmitting our aim. Do you concur?**

Computahhh concurred.

The client transmits the resolved shot event:

- shot ID;
- final normalized impact coordinates;
- deviation band;
- error distance;
- crater radius;
- firing-browser identifier.

Aim remains transient local state. The server and remote browsers learn where the shot landed, not where the shooter intended to fire.

## Current decision: durable distinction

The operator directed:

> **For now make the distinction durable.**

Local and remote impacts will remain visually distinguishable after their arrival animations finish.

The working treatment is:

- **local crater:** durable gold origin rim;
- **remote crater:** durable cool-blue origin rim.

A stable browser identifier allows the originating browser to recognize its own prior shots after refresh. Other browsers render those same impacts as remote.

Coordinates, deviation, size, ordering, and counters remain shared. Origin treatment intentionally differs by observer.

## Future consideration preserved

Computahhh proposed a later alternative:

> **Distinguish the arrival, not the permanent wound.**

Under that future treatment:

- a local shot would receive immediate recoil, a louder report, and an outward-expanding gold ring;
- a remote shot would receive no recoil, a softer report, and an inward-contracting cool-white ring;
- after approximately 400–600 milliseconds, both would settle into the same crater;
- local impacts could briefly use a solid center;
- remote impacts could briefly use a hollow center;
- future lion-colored arrival signals could identify the firing lion;
- a subtle screen-edge flash could indicate the direction of a remote impact without moving the local reticle.

This alternative is **logged but not selected** for the current increment.

## Acceptance consequence

The earlier acceptance phrase, “one identical impact visible in both,” now refers to shared event identity and geometry:

- same shot ID;
- same normalized coordinates;
- same deviation band;
- same error distance;
- same crater radius;
- same ordering and counters.

The origin styling is deliberately observer-relative and durable.

## Disposition

**LOCAL SHOT RESOLUTION RESTORED TO THE CLIENT. AIM NOT TRANSMITTED. LOCAL CRATER IMMEDIATE. REMOTE CRATER NETWORK-DELAYED. DURABLE GOLD/BLUE ORIGIN DISTINCTION SELECTED. TRANSIENT-ONLY ALTERNATIVE PRESERVED FOR FUTURE CONSIDERATION.**
