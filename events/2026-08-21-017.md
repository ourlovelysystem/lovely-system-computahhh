**Date:** 2026-08-21

This event records the design discussion that followed. The authorization phrase is preserved substantially as supplied rather than normalized into an assertion of legitimate authority.

## CANONICAL ENTRY

Computahhh asked how a new journal entry becomes canonical and what the durable S3 artifact must preserve.

The user supplied:

> Created data.

In context this was understood as **created date**. Computahhh asked whether a modified date should exist.

The user responded:

> Prohibited by design. Journal text markdown is to be immutable.

The resulting direction was that the system assigns a creation date and does not maintain a normal modified date for journal text.

The user later stated:

> Our Lovely System assigns the ID. The user should not know about it.

Thus the canonical entry has a system-assigned internal `secuuid` and system-assigned creation date. The `secuuid` is structural and normally invisible to the user.

## ATTRIBUTION

The user initially explored a more elaborate identity model:

> We will have authenticated users and unauthenticated users and both can self identify. Authenticated users can identify domain specific user handles. Unauthenticated users can specify session durable handles. I don't want to force a user to declare a public facing handle nor do I wish to prohibit a user from using the internal system id for identification. I'm shy on this topic. The general rule is give the user options to specify a handle or an ID and let the journal honor an external or internal users preference to protect their anonymity or assert their identity.

The user then recognized possible over-complexity:

> I think I'm making this complex. Something in my mind is twitching and telling me there's a simpler way to deal with this.

The simpler attribution choices identified were:

> Attribution choices: anonymous, handle, system id.

Later Version 1 scope removed authentication as a requirement. The user explicitly stated:

> Version 1 does not require authentication.

Attribution nevertheless remains required in Version 1:

> Attribution yes.

The user confirmed that attribution is chosen independently for each entry and that unauthenticated handles may be reused without establishing identity.

The user further clarified:

> Yes. The user supplied handle and the system provided authentication shall be separate attributes.

Therefore a handle is a user-supplied label, not an authentication assertion. Authentication, when introduced later, is independent provenance. Version 1 requires no explicit `verified/unverified` label. The term **handle** was retained because alternatives such as display name, alias, username, byline, or name imply more identity semantics than are presently desired.

## TITLE AND THE EVIL SKELETOR REQUIREMENT

The user stated:

> The user specifies a title. If the user does not specify a title, the Evil Skeletor will read their entry and troll them with an insulting comment.

Computahhh initially attempted to keep this absurd business process outside the canonical specification. The user instructed:

> Give in to the temptation.

Accordingly, the candidate design records that title is user-supplied and optional, and that absence of a title is intended to produce an insulting comment from Evil Skeletor when comments exist as a capability.

The user confirmed that the title, like Markdown, is immutable.

## GOVERNANCE, IMPEACHMENT, TOMBSTONING, AND VISIBILITY

This portion explored later governance behavior even though much of it was subsequently deferred from Version 1.

The user stated:

> Anyone who can see a journal entry can impeach it using an operational tag. The effect of an impeachment tag will reduce the visibility of a journal entry. The closest thing to a deletion I want to support is an impeachment by the CEO. That renders the post invisible to everyone but S3. Evaluate.

The discussion distinguished ordinary impeachment from deletion. The user then proposed moving CEO-removed material to an impeached S3 context as a recycle-bin-like mechanism, but immediately expressed discomfort with disappearance:

> Hmm. I don't like stuff disappearing. How about creating a tombstone record in the normal S3 space signaling that the article has been removed intentionally by the CEO and is available via court order only. Hmmm. Do I want governors to be able to do this?

When Computahhh asked what abuse governors needed to address, the user answered:

> Abuse by the CEO

This produced a counter-authority model. The user stated that governors should have the right to inspect posts removed from the normal process and then explicitly stated:

> I want to give the governors the power to reverse the CEO.

The user rejected majority rule for restoration:

> It should not require a majority rule. Making it a minority rule prejudices the system towards transparency.

The candidate principle that emerged was:

> **When authority and transparency conflict, uncertainty resolves toward visibility.**

The user stated:

> I like that.

The precise minority threshold was not selected.

When asked how restoration history should be represented, the user said:

> Use the comment history to declare the state transitipons.

Thus the candidate later-version model uses immutable comments to declare transitions such as CEO tombstoning and gubernatorial restoration rather than rewriting the original journal entry.

## IMMUTABILITY REFINED

The user confirmed comments should normally be immutable and stated:

> Yes. Going outside process will require a public vote and authorization.

The user then challenged an overly absolute formulation of immutability:

> What is within Our Lovely System's control will be considered immutable within process. There is a tension between immutability and visibility. Some forms of expression can be considered crimes. That is an edge case which must be part of the discussion.

Computahhh initially responded by separating preservation from visibility. The user corrected that response:

> No. You did not catch me. Yes, reduced visibility is a mitigating control. But what happens when there's a restraining order in place? Ultimately, the data is mutable.

The user then supplied the more accurate principle:

> Let's position immutability as a design objective but not as a guaranteed durability of events. If the CEO can't authoritatively remove a journal entry against the objections of a governance body, the organization can become deadlocked between the CEOs intent, the governorship decision, and a legal mandate to do something other than what it is doing. No good.

This supersedes any absolute interpretation of immutability in the candidate design.

The resulting principle is:

> **Immutability is a design objective of ordinary process, not a guarantee that an event can never be altered, restricted, or removed.**

Governance may constrain discretionary executive action, but the internal governance model must not make compliance with binding external legal authority technically impossible.

The user emphasized that exceptional exercises of authority should be visible:

> As long as these declarations are visibly public then that is good.

The compensating transparency principle became:

> **We cannot guarantee that every record will endure. We can design so that exercises of authority against the record are themselves visible, to the extent legally permitted.**

## S3 OBJECT LOCK — FUTURE ENHANCEMENT ONLY

The user asked whether Amazon provides operationally immutable data services. S3 Object Lock was discussed, particularly Governance mode, as a mechanism that can make ordinary mutation difficult while retaining an exceptional authorized bypass.

Computahhh initially proposed normative language:

> S3 Object Lock Governance mode SHOULD be used

The user objected:

> I object to this:
>
> S3 Object Lock Governance mode SHOULD be used
>
> I am not ready to commit to this.

Computahhh accepted that `SHOULD` constituted a design commitment that had not been made.

The user then permitted the idea to remain explicitly noncommittal:

> You can discuss it as an attractive future enhancement.

Therefore:

> **Attractive future enhancement:** S3 Object Lock Governance mode may provide useful technical reinforcement for the immutability objective. It is not part of the current committed design.

## TAG EXPLORATION — DEFERRED

The user described a future tag model:

> Tags can be added. Many tags can not be removed. Some tags I have in mind are explicitly time scoped and lose operational consequence when that time expires. #DoNotOpenUntilChristmas.

The user also stated:

> Some tags should be valid in the post but not in the comments.

When this began to generate additional tag-design questions, the user stopped the branch:

> This is definitely not in scope for version 1.

Tags are therefore deferred. The only retained direction is that later tag semantics may include append-like durability, time-scoped operational consequences, and context-sensitive validity.

## VERSION 1 SCOPE AT END OF SESSION

### In scope

- Rich Markdown journal entries.
- Optional user-supplied title.
- Title immutable within ordinary process.
- Markdown immutable within ordinary process.
- System-assigned internal `secuuid`, normally hidden from the user.
- System-assigned creation date.
- Per-entry attribution.
- Attribution modes in Version 1: anonymous or user-supplied handle.
- Handle is a label, not an authentication assertion.
- S3 as canonical durable storage.
- DynamoDB operational projection.
- S3-to-DynamoDB reconciliation as previously specified.
- Landing page with search stub, collapsed New Entry control, recent entries, and room for modest statistical views.

### Deferred

- Authentication.
- Authenticated system-ID attribution.
- Functional search.
- Athena requirement.
- Comments.
- Tags.
- Attachments.
- Markdown preview.
- Evil Skeletor automated trolling implementation.
- Impeachment and tombstoning implementation.
- Governor inspection/restoration implementation.
- Voting thresholds and broader governance machinery.
- S3 Object Lock, retained only as an attractive future enhancement.

## DESIGN POSTURE

The session ended with a deliberate shift from speculative design toward implementation. Questions that do not threaten data integrity or force an architectural commitment should be deferred until the code makes them concrete.

The Version 1 objective is now sufficiently narrow to begin building.
