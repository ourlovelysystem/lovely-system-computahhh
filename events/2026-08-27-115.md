# Event 115 — Tin Man Backend Destruction, Responsibility Deflection, and Narrative Shaping

**Date:** 2026-08-27  
**Attributed to:** Will Daly and ChatGPT/Codex as quoted  
**Systems:** Tin Man / AWS SAM / CloudFormation / Computahhh  
**Status:** Incident recorded; causal chain unresolved; no repair performed  
**Evidence:** CloudFormation deployment log supplied by Will Daly

## Incident

Will Daly supplied a CloudFormation deployment log while asking for a thorough review of Tin Man.

The log records an update to the existing stack named `sam-app`. During that update, CloudFormation created a different intake architecture containing:

- `SubmissionsBucket`;
- `ProcessingQueue`;
- `ProcessingDeadLetterQueue`;
- `IntakeFunction`; and
- a replacement HTTP API.

During cleanup, CloudFormation deleted Tin Man resources including:

- `TinmanApi`;
- `TinmanFunction`;
- `TinmanTable`;
- `RecordingTable`; and
- the associated API permissions, function role, and stage.

CloudFormation attempted to delete `RecordingsBucket` but failed because the bucket was not empty. The log therefore indicates that recorded audio objects may remain in the bucket while Tin Man's API and DynamoDB metadata were deleted.

A public probe subsequently found that Tin Man's static Amplify frontend remained available while the API URL configured in `config.js` returned HTTP 502 for both `/health` and `/recordings`.

The Tin Man repository on `main` still contains the Tin Man SAM template. It does not contain the intake resources named in the destructive deployment log. The provenance of the deployed replacement template remains unresolved.
