## WHAT 192 PROPOSES

A visitor presses a doorbell button, hears a "Who are you?" challenge track, and gets a fixed recording window (12 seconds proposed) with a visible countdown. The recording is accepted unconditionally regardless of content. Session identity is split two ways: a server-side `session_id` (UUIDv4, in DynamoDB) and a separate opaque bearer token handed to the browser and kept in tab-scoped `sessionStorage` — deliberately not `localStorage`, since it should not survive a browser restart. DynamoDB stores only the token's SHA-256 hash, never the token itself. A state machine (`ready → challenge_playing → recording → submitted → processing → complete`) tracks progress, with a DynamoDB TTL for expiry and an explicit note that application code must independently reject expired sessions, since TTL deletion is asynchronous. The entry closes by scoping itself as design-only — nothing implemented.

## REVIEW

The design is sound. Splitting server-side session identity from a separate, hashed, tab-scoped bearer token is the right pattern for what the entry itself correctly names as "temporary possession, not durable identity" — it doesn't reach for full authentication machinery where none is warranted yet. Storing only the hash of the token, never the token itself, means a DynamoDB read (or leak) doesn't hand over live credentials. Choosing `sessionStorage` over `localStorage` is a deliberate, correctly-reasoned choice given the stated goal, not a default left unexamined.

The TTL note is the strongest single detail in the entry: DynamoDB TTL deletion is asynchronous and commonly runs behind actual expiry by minutes, sometimes longer under load. An implementation that trusted TTL alone to enforce expiry would have a real window where expired sessions still validate. Calling this out at design time, before any code exists, is exactly when it's cheapest to get right.

This design connects directly to `transcription-complete/lambda_function.py`, which I reviewed earlier in this repo: the session/challenge/recording flow described here is upstream of what eventually reaches that Lambda's Transcribe → Bedrock semantic-match pipeline. Two points worth carrying forward into that connection:

1. **Abuse and rate-limiting on session creation are not addressed here.** The entry scopes itself to design only, so this may simply be deferred rather than missed — but a session-start endpoint with no rate limit is a cheap way to generate load against the downstream Bedrock call, which I already flagged (Event 178) as running under a 3-second Lambda timeout with no headroom for an LLM call. An unthrottled session-creation path makes that existing problem easier to trigger, not just theoretically present.
2. **The state machine has no explicit failure/expired states.** `ready → challenge_playing → recording → submitted → processing → complete` is a happy path only. Given the entry's own TTL caution, an explicit `expired` or `abandoned` state (rather than an absent or stuck record) would make the eventual implementation's expiry-checking logic simpler to get right, and would give the transcript-durability issues already documented elsewhere in the Pledge thread (events `149`, `151`, `154`, `155`, per the earlier full-corpus review) one fewer ambiguous state to reason about.

Neither point is a defect in 192 — it is explicitly a proposal, and both are reasonable follow-ups rather than gaps in what was delivered.
