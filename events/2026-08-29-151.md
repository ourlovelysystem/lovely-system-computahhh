# Event 151 — Transcript Durability Was Double-Counted

**Date:** 2026-08-29  
**System:** Our Lovely System / Pledge / Computahhh  
**Signal:** OPERATOR CORRECTION / DERIVED DATA / HOSTILE REVIEW INVITED  
**Status:** RECOMMENDATION CORRECTED AND PUBLISHED  
**Publication:** Prepared in the public Computahhh repository by explicit direction.

## COMMAND

While designing Pledge's transcription pipeline, Codex recommended storing the complete Amazon Transcribe output in S3 and projecting readable transcript text and metrics into DynamoDB.

Codex then gave a weighted recommendation:

- S3 plus DynamoDB: 90%;
- S3 only: 86%; and
- DynamoDB only: 65%.

The operator objected:

> The transcript is derived from the audio file. Audio file is already on durable storage. I think your estimates factoring s3 durability are therefore less than compelling.

After Codex corrected the analysis, the operator directed:

> Write it up, post a record to Pledge and Computahhh. Invite hostile review.

## INTERPRETATION

The operator identified that the original weighting treated the transcript as though it were independent primary evidence whose loss would destroy the source.

That was incorrect. The borrowed audio already exists durably in S3. A transcript is produced from that audio and can be produced again.

The correction does not establish that repeated transcription will reproduce the exact original provider output. It establishes that S3 durability should not receive full independent credit for preserving both the source and a derivative unless exact historical output has a demonstrated purpose.

## ACTION

Codex recalculated the recommendation with operational catalog usefulness and consistency simplicity weighted more heavily than duplicate durability.

Pledge History 012 was published:

- [Transcript storage recommendation corrected](https://github.com/ourlovelysystem/lovely-system-pledge/blob/main/history/2026-08-29-012-transcript-storage-correction.md)

The Pledge history index was updated.

## RESULT

The corrected present recommendation is:

> **Keep the audio in S3. Put the derived transcript and useful transcription metrics in DynamoDB. Do not create a second S3 transcript artifact until exact historical provider output has a demonstrated use.**

### Corrected weighting

| Criterion | Weight | DDB only | S3 only | S3 + DDB |
|---|---:|---:|---:|---:|
| Catalog usefulness | 30% | 10/10 | 4/10 | 10/10 |
| Simplicity and consistency | 25% | 10/10 | 8/10 | 5/10 |
| Historical processing evidence | 15% | 7/10 | 10/10 | 10/10 |
| Rebuildability from audio | 10% | 9/10 | 10/10 | 10/10 |
| Size tolerance | 10% | 6/10 | 10/10 | 9/10 |
| Reporting and analysis | 10% | 6/10 | 9/10 | 9/10 |
| **Weighted result** | **100%** | **89%** | **77%** | **83%** |

These scores are structured judgments rather than measured probabilities.

## CORRECTED DATA RELATIONSHIP

```text
S3 audio
  = durable borrowed asset
  = source for reconstruction

DynamoDB transcript
  = derived operational interpretation
  = useful catalog data

S3 transcript artifact
  = deferred historical evidence
  = justified only by a demonstrated need
```

The intended DynamoDB projection includes:

- transcript text;
- transcription status;
- provider job identity;
- completion time;
- language;
- word count;
- recognized duration;
- mean and minimum confidence;
- transcription policy version;
- semantic match score;
- content decision; and
- content reason.

## LIMIT OF THE CORRECTION

“Derived” does not mean “perfectly reproducible.”

A later transcription can differ because:

- provider models change;
- language identification changes;
- punctuation behavior changes;
- confidence calibration changes;
- vocabulary settings change; or
- Pledge changes its transcription policy.

If the historical transcript caused Pledge to accept, reject, publish, use, or purge an electronic valuable, the exact original interpretation may itself become consequential evidence.

That possibility reduces confidence in DynamoDB-only transcript storage. It does not restore the original durability weighting without a demonstrated requirement to preserve exact provider output.

## HOSTILE REVIEW INVITED

Pledge and Computahhh invite hostile review of the corrected recommendation.

The requested attack surface includes:

1. Is a transcript genuinely reconstructable if the model that produced it changes?
2. Does retranscription rebuild evidence or replace history?
3. Once a transcript drives a consequential decision, does it cease to be merely derived data?
4. Does storing the transcript only in DynamoDB violate Our Lovely System's S3-first reconstruction rule?
5. Is avoiding a tiny S3 storage cost false economy?
6. Can DynamoDB's 400 KB item limit become an avoidable failure surface?
7. Should exact provider output be preserved selectively for rejected, disputed, reviewed, or used recordings?
8. Does the catalog contain enough processing context to make a later result comparable?
9. Can trusted-user transcript inspection be provided without creating a new privacy vulnerability?
10. What evidence would prove that preserving complete provider output creates value?

> **Do not accept “derived” as a synonym for “disposable.” Attack the premise.**

The invitation has been placed on the existing [Pledge hostile-review issue](https://github.com/ourlovelysystem/lovely-system-nasty-oracle/issues/1).

## COMPUTAHHH COMMENTARY

The original recommendation sounded architecturally responsible because it repeated an established truth: S3 is durable and DynamoDB is rebuildable.

The truth was applied lazily.

The system already possessed the durable source. Awarding another large durability benefit for storing the derivative in S3 made redundancy look like preservation without first proving what historical fact needed preservation.

The operator's objection did not prove that provider output lacks evidentiary value. It forced the value to identify itself before acquiring infrastructure.

That is the better burden:

> **Do not preserve a derivative merely because preservation is cheap. Identify what its loss would prevent us from knowing.**

## CORRECTION

The prior 90% recommendation for storing transcript output in both S3 and DynamoDB is superseded.

The current recommendation is 89% for storing the transcript and useful metrics in DynamoDB while retaining the audio as the durable S3 source.

No transcription pipeline has been implemented by this correction.
