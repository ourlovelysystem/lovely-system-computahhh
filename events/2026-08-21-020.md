# Journal Version 1 — First Successful Infrastructure Deployment

**Date:** 2026-08-21

## Summary

Our Lovely System Journal advanced from design into its first successfully deployed AWS backend.

The implementation began from a fresh repository and a deliberately constrained Version 1 scope. The journal permits unauthenticated use, supports per-entry attribution as either anonymous or a user-supplied handle, keeps authentication as a separate future concern, treats title and Markdown as immutable within ordinary process, uses S3 as the canonical durable record, and uses DynamoDB as a rebuildable operational projection.

Search, comments, tags, attachments, authentication, and Markdown preview remain deferred. The frontend includes a search stub, a collapsed New Entry form, recent entries, and room for simple statistical views. Untitled submissions trigger transient Evil Skeletor abuse without introducing the deferred comment system.

## AWS SAM Tooling

The backend is defined with AWS SAM, which expands into CloudFormation resources.

The local machine initially had no SAM CLI installed. The first Homebrew installation attempt exposed two facts:

1. the shell was invoking Homebrew through Rosetta while Homebrew itself lived in the ARM prefix; and
2. the old AWS Homebrew tap for SAM was deprecated.

SAM CLI was then successfully installed natively and verified as:

`SAM CLI, version 1.165.0`

`sam build` completed successfully. The absence of `requirements.txt` files was acceptable because the Lambda functions rely only on Python standard library modules and `boto3`, which is available in the Lambda runtime.

## First Deployment Attempt — Circular Dependency

The original template used a direct S3 object-created notification to invoke the projector Lambda.

CloudFormation rejected the stack with a circular dependency involving the S3 bucket, projector Lambda, Lambda permissions, IAM roles, API resources, and reconciliation resources.

The projection path was changed from:

`S3 -> Lambda -> DynamoDB`

to:

`S3 -> EventBridge -> ProjectFunction -> DynamoDB`

The functional intent remained the same while the direct dependency cycle was removed.

## Bucket Naming

The initial template allowed CloudFormation to generate the physical S3 bucket name.

The user objected to the resulting naming approach and selected:

`ourlovelysystem-journal`

The template was changed to request that exact bucket name.

The first failed stack had already created resources before rollback, so the earlier assumption that no physical bucket had ever been created was corrected. Rollback successfully removed the temporary resources.

The final deployment later confirmed that `ourlovelysystem-journal` was available and was successfully created.

## Second Deployment Attempt — CORS Failure

The next deployment progressed substantially farther. S3, DynamoDB, IAM roles, and Lambda functions were created successfully.

API Gateway then failed with:

`Duplicated values are not allowed in allow-origins`

The cause was duplicate CORS configuration: CORS had been declared both in `Globals.HttpApi` and explicitly on `JournalApi`. SAM merged those values, producing duplicate allowed origins.

The global CORS declaration was removed and the explicit `JournalApi` CORS configuration retained.

CloudFormation rolled the failed stack back to `ROLLBACK_COMPLETE`. The failed stack was then deleted so that a fresh stack could be created.

## Successful Deployment

After the circular dependency and duplicate-CORS defects were corrected, the stack deployed successfully in:

`us-east-1`

Stack name:

`lovely-system-journal`

Confirmed outputs included:

## Current Architecture

```text
Browser
  |
  v
API Gateway
  |
  +--> SubmitFunction
  |      |
  |      v
  |     S3  (canonical JSON)
  |      |
  |      v
  |  EventBridge
  |      |
  |      v
  |  ProjectFunction
  |      |
  |      v
  |   DynamoDB  (operational projection)
  |
  +--> ListFunction --> DynamoDB

ReconcileFunction:
  S3 <-> DynamoDB inspection and repair
  S3 remains source of truth
```

The reconciliation process preserves the previously agreed two-part rule:

1. every object represented in DynamoDB must correspond to an S3 object, and every S3 journal object must have a DynamoDB projection; and
2. a JSON-aware comparison replaces any mismatching DynamoDB document with the complete S3 JSON document.

S3 remains authoritative.
