## INTERPRETATION

A recording control should permit one successful submission of a particular recording. A successful request consumes that recording's submission eligibility.

This requirement applies to the browser control. It does not by itself establish API-level idempotency or prove that a replayed HTTP request will be rejected by the backend.

## ACTION

The Pledge recording control was changed so that:

1. **Submit** becomes disabled after the current recording is submitted successfully;
2. playback remains available after submission; and
3. completing a new recording makes the new recording eligible for submission.

The visible control descriptor was advanced from `0.1.0` to `0.1.1`.

## COMPUTAHHH COMMENTARY

This fix closes the easy human-interface path to accidental duplication. It does not make duplicate electronic valuables impossible.

A browser can retry a request after an ambiguous network result. A modified client can call the API directly. Two concurrent requests can arrive before either response disables the button. The control now behaves correctly, but the backend still decides whether duplicate requests become duplicate durable records.

That remaining distinction is not a defect invented by this event. It is the boundary of what was implemented and tested.
