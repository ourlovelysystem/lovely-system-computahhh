## Infrastructure created

The test is hosted as part of the working `lovely-system-teambuilder` application.

### Public client

- Public application: `https://teambuilder.ourlovelysystem.org/shooting-gallery/`
- Static frontend deployed through the existing Teambuilder web-hosting path.
- Canvas-based shooting field with target, reticle, recoil, impact deformation, shot classification, counters, and persistent visible impacts.
- Immediate local rendering: a local shot is displayed without waiting for an AWS round trip.
- Durable origin distinction: shots produced by the current client receive a gold rim; shots received from another client receive a blue rim.
- Deterministic test identities are available through the narrow `?client=<name>` test hook. This permits Alpha, Bravo, Charlie, and Delta to remain distinct even when hosted inside one browser profile.

### Shared backend

- AWS SAM and CloudFormation stack: `lovely-system-shared-shooting-gallery`.
- Region: `us-east-1`.
- API Gateway WebSocket endpoint for persistent bidirectional client connections.
- Python 3.13 Lambda function on arm64 handling connect, disconnect, join, fire, default, and target-replacement routes.
- DynamoDB connection table retaining active room connections with expiration.
- DynamoDB state table retaining authoritative room generation, sequence, counters, accumulated error, and impact records.
- Shared room: `gallery-main`.
- Configured impact ceiling: 500.
- Server path validates a completed impact, updates authoritative state, increments sequence and counters, and broadcasts the accepted result to connected clients.

The client does not transmit aim. It transmits the completed impact produced by the local weapon model. The server does not tell the initiating client what that client already knows before permitting local display. It validates, records, and distributes the shared consequence.

## Primitive under investigation

The underlying primitive is not merely a shooting gallery.

It is:

> **Independent sessions produce local events; a shared authority accepts those events; every participant receives the accepted consequences; the group converges on a common state.**

This is a foundation for the earlier shared-button concept:

> Within a prescribed interval `T`, an aggregate event may occur when `N` independent sessions each produce a qualifying event.

The present increment does not yet perform the complete `N-within-T` aggregation rule. It establishes supporting behavior:

- independent client identity;
- immediate local action;
- real-time transport;
- authoritative acceptance;
- broadcast of consequences;
- local-versus-remote provenance;
- shared counters and state convergence;
- visible tolerance of remote lag without sacrificing local responsiveness.

## Representation in more complex cooperative modules

The primitive can support later Teambuilder modules in which:

- several lions must act within a common time window;
- normal targets require up to `N` team hits;
- abnormal targets require `N+1` hits outside a reticle but `N-1` hits inside it;
- moving objects cross or avoid a shared reticle;
- players choose between tracking targets of opportunity and maintaining coordinated focus;
- three independently controlled Venn spheres overlap and become a common white reticle when cooperation is sufficient;
- misses, friendly fire, asymmetric incentives, and ambiguous intent affect team cohesion;
- an aggregate action exists only when multiple independent local actions satisfy a shared rule.

The shooting gallery therefore tests a small reusable social-mechanical unit: local agency entering a shared field and becoming a common consequence.

## Witness test to be performed

The next defensible test must be a continuous-evidence test. It must not reconstruct timing from intermittent screenshots.

### Preconditions

1. Replace the shared target once.
2. Confirm the authoritative zero state on every client.
3. Display four distinct connected clients simultaneously: Alpha, Bravo, Charlie, and Delta.
4. Begin one uninterrupted recording before the first shot.
5. Show a continuous monotonic clock, client identities, client counters, connection state, and authoritative server sequence.
6. Begin a machine-readable event trace at the same boundary.

### Performance

1. Alpha fires a nine-shot upper-left volley, spreading within the quadrant while drifting from outside the reticle into it and back out.
2. Wait between three and five seconds after Alpha's volley ends.
3. Bravo repeats the pattern in the upper-right quadrant.
4. Wait between three and five seconds.
5. Charlie repeats the pattern in the lower-left quadrant.
6. Wait between three and five seconds.
7. Delta repeats the pattern in the lower-right quadrant.
8. Continue recording until every connected client visibly converges.

The shots must occur at the performed cadence. Capture work must not interrupt a volley. Post-production must not manufacture pauses, compress gaps, create transitions, or imply continuous behavior that the original recording does not contain.

## Expected results

### Functional expectations

- Every local shot appears immediately in the initiating client.
- Every accepted shot is transmitted through the deployed WebSocket and Lambda path.
- Every connected client eventually renders every accepted impact.
- The firing client marks its own impacts gold.
- Other clients mark those same impacts blue.
- Each completed volley adds nine authoritative shots.
- Counters may diverge temporarily while broadcasts travel.
- Counters converge after each volley.
- Final authoritative and client shot counts converge at 36.
- Final authoritative sequence advances once per accepted shot.
- The four displays contain the same impact set while preserving client-relative provenance colors.
- No client requires a reload to receive ordinary fire or the final converged state.

### Evidentiary expectations

- The original recording begins before action and ends after convergence.
- The clock remains visible and uninterrupted.
- The original event trace records shot identifiers, shooter identities, server sequence, and relevant local/server receive times.
- Video and trace agree on order and count.
- Cryptographic hashes are recorded for the original recording and trace.
- Original files are preserved unchanged.
- Any layout, trimming, captioning, or derivative edit is labeled and linked back to the originals.

## Failure conditions

The test fails if any of the following occurs:

- a client misses an accepted shot;
- clients do not converge without reload;
- server sequence or counters disagree with the accepted impact set;
- client identity collapses across panes;
- local display waits on a server round trip;
- capture activity interrupts the required firing cadence;
- the recording has an unexplained gap;
- post-production authors timing or continuity;
- the original recording or trace is not retained;
- a derivative is presented as the original witness record.

## Evaluation

The deployed infrastructure has already demonstrated real multi-client transport, immediate local response, perceptible remote lag, and eventual convergence. An independently open local instance also received shots created during remote testing, providing additional evidence that the public shared path was active.

However, the prior MP4 artifacts do not prove continuous performance. They were reconstructed from intermittent captures, and authored frame timing overstated what had been recorded. Event 079 records that evidentiary failure.

The current infrastructure is therefore sufficient to continue functional experimentation but insufficient, by itself, to produce the required witness artifact. The missing component is a recording and tracing surface designed around evidence provenance rather than presentation.

The correction is not to polish the reconstruction. The correction is to build Witness Mode and execute a new test under the procedure above.
