**Time:** 2026-08-21 10:27 EDT

## SUBJECT

Ledger storage, query architecture, and OpenSearch candidate analysis.

## BACKGROUND

Our Lovely System is considering a Markdown-based ledger. Each journal entry receives a stable `secuuid`. Future resource families such as attachments, comments, and tags are intended to remain separate and associate back to journal entries through the `secuuid`, rather than being nested into one entry hierarchy.

Pass 1 is intentionally narrow: rich Markdown, durable storage, performance, paging, and search. Attachments, tags, comments, voting, reputation, and utility mechanisms are deferred so that the first implementation remains small enough to determine whether it actually works.

## EPISTEMIC TRAIL — QUESTIONS THAT PRODUCED THIS DIRECTION

This record is not intended to present the resulting architecture as received wisdom. The following sequence records the questions, competing ideas, objections, and observations that caused the current position to emerge. Future reviewers should re-run these questions against the technology, prices, workloads, and operational experience available to them.

### 1. What role should DynamoDB have?

The starting proposition was deliberately skeptical of DynamoDB: use it strategically for searching, paging, and updating, but keep S3 as the durable system of record; nothing in DynamoDB should be irrecoverable from S3.

The challenge to that proposition was that DynamoDB is genuinely better than S3 for live operational state, conditional updates, atomic counters, concurrency control, and predetermined access paths. The resulting refinement was not "nothing important should live in DynamoDB," but rather:

> Nothing important may exist only in DynamoDB.

This permits DynamoDB to be operationally important while remaining reconstructible.

### 2. How small should Pass 1 be?

Tag reputation, utility credits, voting, comments, and attachments were discussed as future capabilities. They were explicitly removed from Pass 1 because a feature-rich first implementation could become too complicated to answer the basic question: does the ledger work?

Pass 1 therefore became rich Markdown + S3 durability + performance + paging + search. Attachments remain a known coming requirement, but are not implemented in this pass.

### 3. How should future resource families be arranged in S3?

A proposal to organize data under each entry was rejected:

```text
journal/<secuuid>/attachments
journal/<secuuid>/tags
```

The preferred model keeps resource families separate:

```text
journal/<secuuid>
attachments/<secuuid>/...
comments/<secuuid>/...
tags/<secuuid>/...
```

The reason is not cosmetic. It permits each resource family to have its own lifecycle and query behavior while `secuuid` supplies the relationship.

### 4. Why did Athena affect the layout discussion?

Prior journal experimentation suggested that Athena and binary-heavy/mixed object hierarchies are an uncomfortable combination. The question became whether ACLs, IAM restrictions, path filtering, manifests, or other clever mechanisms could let Athena selectively traverse a mixed hierarchy.

Those techniques can work. They were nevertheless judged brittle as the semantic definition of the dataset. An incorrectly configured permission could subtly alter what Athena sees while queries continue to return plausible-looking results.

This produced the design principle:

> Permissions should enforce security boundaries, not define the meaning of the dataset.

Physical separation of journal text from attachment binaries is therefore preferred because it is boring, visible, and inspectable.

### 5. What questions should DynamoDB answer, and what questions should Athena answer?

A keyword query was used as a test case: find journal entries containing a phrase over a historical period. Athena naturally searches the S3 corpus and returns matching `secuuid` values.

A DynamoDB-only example — chronological paging — exposed a temptation to introduce awkward time-bucket key schemes. That was rejected as premature complexity for a low-traffic journal containing tens of thousands rather than billions of entries.

The useful distinction became:

> DynamoDB is strongest when the access path is known in advance. Athena is strongest when a human invents a question later that was not encoded into a DynamoDB key design.

Examples considered included time ranges, authors, tags, keyword searches, comments, attachment metadata, and combinations of these criteria.

### 6. Does OpenSearch solve the query problem more cleanly?

Yes, functionally. OpenSearch was identified as the strongest direct match for rich interactive full-text search, relevance ranking, tags, times, comment text, attachment metadata, and compound filters.

This challenged whether DynamoDB was needed for search at all. A potential architecture was:

```text
S3 canonical record
       |
       v
OpenSearch searchable projection
       |
       v
application
```

The objection was economic and operational rather than functional. The project has not yet demonstrated that sophisticated interactive search is valuable enough to justify buying and maintaining a dedicated search projection.

### 7. How do costs behave as workload changes?

S3 + DynamoDB + Athena was compared with S3 + OpenSearch across low, moderate, and heavy workloads.

The important shape of the cost curves was more useful than a single price estimate:

- S3 is inexpensive durable bulk storage.
- DynamoDB can remain inexpensive with a small projection and low traffic.
- Athena charges principally when queries scan data.
- OpenSearch performs indexing work in advance to make searches fast, introducing a different compute/index cost profile.

This suggested using Athena until search frequency, latency expectations, or query sophistication demonstrate that a maintained search index has earned its cost.

### 8. What if users deliberately try to increase the AWS bill?

A hostile-cost scenario was introduced: enemies deliberately generate traffic to tax infrastructure and escalate costs.

This materially affected the evaluation. The desired behavior is not infinite automatic scaling. The desired behavior is controlled degradation:

> Under attack, an expensive feature may stop working before infrastructure spending is allowed to grow without a deliberately selected ceiling.

DynamoDB throughput controls, Athena query/workgroup scan controls, API throttling, and related safeguards make the S3/DynamoDB/Athena approach attractive for a system that values economically bounded failure.

### 9. Are we replicating data into Athena?

No, not in the simple model. Athena queries data where it already resides in S3. An Athena-optimized Parquet projection could be introduced later, but doing so would be an earned optimization rather than a Pass 1 requirement.

DynamoDB, by contrast, does contain a derived copy/projection of selected S3 information.

## STORAGE DIRECTION

The working architecture assigns different responsibilities to three AWS services:

- **Amazon S3:** canonical durable system of record.
- **Amazon DynamoDB:** rebuildable operational projection for fast known access patterns, paging, and current lookup state.
- **Amazon Athena:** flexible and ad-hoc querying over data in S3, including keyword/content searches that do not map naturally to DynamoDB keys.

The governing constraint is that nothing important should exist only in DynamoDB. If DynamoDB is destroyed, S3 should contain sufficient information to reconstruct the projection.

## OPENSEARCH ANALYSIS

OpenSearch remains the strongest candidate if rich interactive search becomes a central product requirement. Its rejection at this stage is provisional, not doctrinal. Future reviewers should reconsider it if query volume, latency expectations, costs, or AWS service characteristics change.

## CURRENT CONCLUSION — SUBJECT TO REEXAMINATION

The present direction is intentionally conservative:

> S3 remembers. DynamoDB makes known access patterns fast. Athena answers questions we did not design DynamoDB keys to answer.

This is a decision under current assumptions, not an assertion that these technologies possess permanent roles.
