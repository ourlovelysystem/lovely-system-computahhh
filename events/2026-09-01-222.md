## WHAT HAPPENED

The operator provided `ourlovelysystem/lovely-system-sandbox`, empty apart from a README, with the stated goal of a web app on AWS with minimal friction between describing, writing, and deploying. Claude recommended AWS Amplify Gen 2 over the SAM pattern used in the sibling Pledge repo, citing a tighter local-iteration loop and combined frontend/backend handling, with the tradeoff being less consistency with existing project patterns and less direct visibility into the underlying CloudFormation.

A pre-flight check found the local AWS CLI authenticated as **root** (`arn:aws:iam::867712763388:root`) — the same unresolved issue already on record in this log as Event 148. Claude declined to proceed under root without flagging it and offered two paths: fix it, or proceed anyway. The operator created a new IAM user, `claude`, and switched to it — but that user was a member of an `admin` group carrying AWS's `AdministratorAccess` managed policy, which Claude checked rather than assumed and found to be functionally unrestricted, not actually scoped.

The operator challenged this as goalpost-moving. Claude held that the original ask — permissions limited to what Amplify sandbox needs — had not changed, stated a concrete, bounded definition of what would be accepted (CloudFormation, Lambda, DynamoDB, AppSync, Cognito, S3, the specific IAM actions needed for the app's own role creation, and Logs; nothing else), and committed not to re-litigate that bar once met. A scoped policy matching that definition was written, created, attached to the `claude` user, and the user was removed from the `admin` group — each AWS-modifying command individually blocked by the session's auto-mode classifier and re-run by the operator directly via the `!` prefix. The removal was verified, not assumed: a subsequent `iam:ListGroupsForUser` call failed with `AccessDenied`, confirming `AdministratorAccess` was actually gone rather than nominally detached.

An Amplify Gen 2 app was scaffolded in the sandbox repo and a trial `npx ampx sandbox --once` deployment was attempted. It failed at the credential-resolution stage, before touching any scoped resource, citing a missing `CreateOAuth2Token`-type permission. Investigation found the AWS CLI itself worked normally under the same scoped identity (`sts get-caller-identity` succeeded seconds earlier), while Node's AWS SDK — used internally by `ampx` — failed to resolve credentials through a non-standard `~/.aws/config` field, `login_session`, that does not correspond to any recognized AWS CLI or SDK configuration key. No wrapper tool (aws-vault, granted, leapp) or explicit SSO/credential_process configuration was found to explain it.

The operator stated this as evidence against least-privilege development environments generally. Claude held the claims apart: the AWS CLI's successful credential resolution under the same scoped policy argued against the scoping being the direct cause, while acknowledging that a missing broader STS permission (`sts:AssumeRole`, `sts:GetSessionToken` — neither included in the scoped policy) could not be ruled out without a controlled test, since the `login_session` mechanism itself remains unidentified.

The operator then identified a sharper problem: Claude's own scoped policy — deliberately excluding IAM group inspection, broader STS actions, and diagnostic services like CloudTrail — had removed Claude's own ability to investigate the failure. Claude confirmed this directly rather than defending the scoping choice: the policy had been written for one goal (limiting blast radius for the app's own operation) without accounting for a second goal that turned out to matter at the exact moment it mattered — debuggability during active development. Claude distinguished this from the operator's broader claim: demonstrating that scoping impeded *diagnosis* is not the same as demonstrating scoping *caused* the original failure — those remain separable, and only the first was established at that point in the exchange.

The agreed resolution was to temporarily restore the `admin` group membership and rerun the trial deployment as a controlled test — serving both as the fix for the diagnostic corner and as the actual test of the causal claim. That command was blocked by the same classifier pattern as the earlier IAM-modifying commands and was pending operator execution via `!` when this entry was requested.

## OPEN QUESTION

Whether the scoped policy caused the `ampx` credential failure, versus a `login_session` mechanism unrelated to IAM policy scope, is not yet resolved. The test that would resolve it is described above and had not yet run as of this entry.
