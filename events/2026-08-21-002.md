# Event 2026-08-21-002

**Time:** 2026-08-21 10:27 EDT

## SUBJECT

S3-to-DynamoDB projection model and replication failure taxonomy.

## BACKGROUND

Our Lovely System's proposed ledger uses Amazon S3 as the canonical durable record and Amazon DynamoDB as a rebuildable operational projection. For journal content, the intended processing model is:

```text
User/API
   |
   v
Validate
   |
   v
S3 PutObject
   |
   v
S3 event
   |
   v
Lambda projector
   |
   v
DynamoDB projection
```

A DynamoDB journal record must never be considered more authoritative than the S3 object from which it was derived. Deleting a DynamoDB projection must not delete the canonical S3 journal entry.

## EPISTEMIC TRAIL — HOW THE HOLE WAS FOUND

This conclusion emerged through a short sequence of questions rather than from an initial requirement. The sequence is preserved because future engineers should be able to challenge the conclusion using their own operational experience.

### Question: When does DynamoDB receive the projection?

Answer: after the canonical S3 write succeeds. The proposed mechanism was:

```text
S3 PutObject
   |
   v
S3 event
   |
   v
Lambda
   |
   v
DynamoDB upsert
```

This established a clear direction of authority: a DynamoDB journal projection should never precede the durable S3 record it represents.

### Question: What happens if someone deletes an entry from DynamoDB?

Answer: the S3 journal object remains intact. The operational projection disappears, so DynamoDB-driven queries may cease to show the entry even though the canonical ledger still contains it.

That answer exposed the important distinction between **durability** and **visibility/correctness of the projection**.

The architecture successfully prevents a DynamoDB deletion from destroying the ledger. It does not, by itself, prevent the application from presenting an incomplete or incorrect view of the ledger.

### Observation: the plan has a replication hole

Experience with replication failure points prompted the question whether there is a taxonomy for the anomalies that can occur between S3 and DynamoDB.

The relevant categories identified were:

- write-order failure;
- delivery failure;
- duplicate delivery;
- out-of-order delivery;
- partial projection failure;
- divergence;
- deletion asymmetry;
- poison records;
- reconciliation failure;
- schema/version skew.

The processing model was then scored against each category rather than merely asserting that event-driven replication was reliable.

This changed the design conversation. The original event flow described **how DynamoDB gets updated**. It did not answer **how we know DynamoDB is correct**.

That is the epistemic distinction this record is intended to preserve.

## REPLICATION FAILURE TAXONOMY

The following anomaly classes were scored for vulnerability of the current model on a 1-5 scale, where 5 represents the greatest concern. These scores assume the basic S3-event/Lambda/DynamoDB projection flow and that an independent reconciliation mechanism has not yet been implemented.

| Replication anomaly | Vulnerability | Current concern |
|---|---:|---|
| Write-order failure | 1/5 | S3 is deliberately written first, preventing the projection from becoming durable truth ahead of the canonical record. |
| Delivery failure | 4/5 | If projection processing is not successfully delivered/completed, DynamoDB can remain incomplete. |
| Duplicate delivery | 2/5 | Expected to be manageable through idempotent projection writes. |
| Out-of-order delivery | 4/5 | An older projection event can overwrite newer projected state unless versions are explicitly compared. |
| Partial projection failure | 3/5 | A projector may succeed partially as the projection becomes more complex. |
| Divergence | 5/5 | The largest current weakness: nothing independently proves that DynamoDB still represents S3 correctly. |
| Deletion asymmetry | 4/5 | Deleting a DynamoDB item can make an existing S3 entry disappear from DynamoDB-driven views until repaired. |
| Poison record | 3/5 | Malformed or unexpected canonical data may repeatedly fail projection processing. |
| Reconciliation failure | N/A yet | Reconciliation has not yet been designed; therefore its own failure modes cannot yet be scored. |
| Schema/version skew | 3/5 | Different projector versions may interpret the same durable S3 data differently. |

The current overall replication robustness was estimated at approximately **2.5/5**. This does not mean the durable ledger is fragile. S3 protects the canonical record well. The weak point is confidence that the DynamoDB operational representation is complete and correct at any given time.

## WHY PLAUSIBLE WRONGNESS IS THE PRIMARY CONCERN

A hard failure is comparatively visible. If DynamoDB is unavailable, the system knows it has a problem. If one projection silently disappears or becomes stale, however, the journal can continue functioning while returning believable but incomplete results.

For a ledger, that failure is epistemically worse: users may believe they are observing the record when they are actually observing a damaged projection of the record.

Therefore divergence was scored 5/5 even though the canonical S3 data remains safe.

## IDENTIFIED DESIGN REQUIREMENT

The simple event-driven projection path is insufficient as the sole integrity mechanism.

The emerging model requires two logically independent mechanisms:

```text
CONTINUOUS PROJECTION
S3 -> event -> Lambda -> DynamoDB

INDEPENDENT RECONCILIATION
S3 canonical corpus -> compare/verify -> DynamoDB
```

Continuous projection answers:

> How does DynamoDB become current?

Reconciliation answers:

> What evidence do we have that DynamoDB actually represents S3?

The independence matters. A verification mechanism that merely repeats the same assumptions and failure path as the projector may reproduce the same error rather than detect it.

## QUESTIONS LEFT FOR FUTURE EXAMINATION

No reconciliation implementation has yet been selected. Future work should examine at least:

- what constitutes proof of equivalence between canonical S3 state and DynamoDB projection;
- whether verification should compare counts, identifiers, hashes, versions, or reconstructed records;
- how often reconciliation should run;
- whether repair should be automatic or merely reported;
- how reconciliation itself is audited;
- how to detect a faulty projector that consistently produces plausible but incorrect data;
- how schema migrations alter the meaning of equivalence.

These are open questions, not implied implementation requirements.

## CURRENT CONCLUSION — SUBJECT TO REEXAMINATION

> S3 is authoritative. DynamoDB is rebuildable. Therefore DynamoDB divergence must be detectable and repairable independently of the event path that created the projection.

The important result of this discussion is not merely "add reconciliation." It is the recognition that **replication needs an epistemology: the system must have a way to establish what it knows about the correctness of its own projection.**
