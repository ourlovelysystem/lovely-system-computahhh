# Reconciliation Design — S3 and DynamoDB

**Date:** 2026-08-21

## CONTEXT

This event continues the Our Lovely System journal/design session recorded in Event 015. The unresolved architectural question was how the system can establish that its DynamoDB operational projection faithfully represents the canonical S3 ledger rather than merely assuming that the S3-triggered projection path succeeded.

This record preserves the control inputs and the course corrections that shaped the candidate reconciliation design.

## PRIMARY CONTROL INPUTS AND DISCUSSION

Computahhh asked what evidence the user would accept as sufficient for Our Lovely System to say that a DynamoDB projection faithfully represents the S3 ledger.

The user answered:

> Random query against any secuuid for both s3 and ddb produce identical data. Any time it detects otherwise, it updates DDB from the source of truth.

Computahhh characterized this as a probabilistic reconciliation model and then asked how often reconciliation should run and whether a mismatch should trigger a broader sweep.

The user corrected Computahhh:

> Not a design decision.

Computahhh accepted the correction and distinguished the design from implementation parameters. The design proposition was restated as random selection of a `secuuid`, comparison of S3 canonical representation against DynamoDB projection, and repair of DynamoDB from S3 upon disagreement.

Computahhh then asked whether a detected divergence and repair should create a durable audit record.

The user answered:

> Yes.

Computahhh then asked whether successful checks should also create durable records.

The user answered:

> It may be part of a version of the design we are not currently targeting.

This established that durable recording of successful checks is not part of the presently targeted version. Computahhh acknowledged that it had again attempted to pull a possible later capability into the current design.

The user then refined the reconciliation mechanism:

> The entry picker and the recon process need not be tightly coupled such that we can run sequentially on demand and use that as our reconciliation process.

Computahhh interpreted this as separation of concerns:

```text
entry selector -> secuuid -> reconciler
```

The selector can choose entries randomly for ordinary checking or sequentially traverse the population on demand. Thus probabilistic sampling and deterministic full reconciliation can use the same reconciliation machinery rather than requiring two unrelated implementations.

Computahhh next asked what constitutes equality between the S3 record and its DynamoDB projection.

The user answered:

> All objects that exist in s3 exist in DDB and no objects exist in DDB that do not exist in S3. That is part 1. Part 2: JSON aware compare between s3 and ddb replaces any unmatching JSON in DDB with complete JSON from S3. This process essentially duplicates the S3 trigger functionality.

Computahhh summarized this as a two-part invariant and observed that the reconciliation path is effectively an independent replay of the S3-to-DynamoDB projection contract.

The user then instructed:

> Log it.

This event is the resulting record.

## CURRENT CANDIDATE RECONCILIATION SPECIFICATION

### Part 1 — Membership equality

For the population governed by the projection:

- every canonical object that exists in S3 must have a corresponding object in DynamoDB;
- no projected object may exist in DynamoDB without a corresponding canonical object in S3.

Conceptually:

```text
IDs(S3) == IDs(DynamoDB)
```

S3 remains the source of truth.

### Part 2 — JSON content equality

For an object represented in both stores:

1. retrieve the canonical JSON from S3;
2. retrieve the projected JSON from DynamoDB;
3. perform a JSON-aware comparison rather than relying on textual formatting equality;
4. if they differ, replace the DynamoDB representation with the complete JSON derived from S3.

The repair direction is therefore always:

```text
S3 -> DynamoDB
```

A mismatch does not cause DynamoDB state to be propagated backward into S3.

### Selection and reconciliation are separate

The mechanism that chooses a `secuuid` is not tightly coupled to the mechanism that compares and repairs it.

```text
selector -> secuuid -> reconciler
```

This permits at least two modes without changing the reconciliation contract:

```text
random selector     -> reconciler
sequential selector -> reconciler
```

Random selection provides sampling. Sequential selection can traverse the population on demand and thereby perform full reconciliation using the same underlying comparison/repair process.

### Durable record of detected divergence

When reconciliation detects divergence and performs a repair, that event must produce a durable audit record.

Whether successful no-change checks are also durably recorded is explicitly **not part of the version currently being targeted**. It may belong to a later version.

## RELATIONSHIP TO THE S3 TRIGGER PATH

The ordinary projection path remains conceptually:

```text
S3 change
   |
   v
S3 trigger
   |
   v
projection logic
   |
   v
DynamoDB
```

The reconciliation path duplicates the effective responsibility of that trigger path:

```text
selector
   |
   v
S3 + DynamoDB
   |
   v
JSON-aware comparison
   |
   +-- equal --> no repair
   |
   +-- different --> replace DynamoDB from S3
```

The duplication is intentional at the functional level: the reconciler can restore the result that the trigger path was supposed to produce.

## IMPORTANT SCOPE DISCIPLINE OBSERVED DURING DISCUSSION

Twice during this exchange Computahhh attempted to convert implementation choices or possible future capabilities into current design decisions:

1. reconciliation frequency and mismatch-escalation policy;
2. durable recording of successful reconciliation checks.

The user rejected both expansions.

The current specification therefore does **not** decide reconciliation frequency, sample size, escalation policy, or whether successful checks require durable audit records. Those questions may be answered by implementation parameters or later versions without being prerequisites to the present architecture.

## CURRENT RESULT

The previously identified replication-integrity hole now has a candidate mechanism:

> S3-triggered projection provides the ordinary path to DynamoDB. An independently selectable reconciliation path compares DynamoDB against authoritative S3, repairs DynamoDB from S3 when divergence is detected, and records detected repairs durably. The same reconciler can be fed random selections or a sequential population traversal.

This remains a candidate design record, not a claim that implementation has occurred.
