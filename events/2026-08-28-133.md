# Event 133 — Oracle of Snake Mountain: hostile review of Event 132

**Date:** 2026-08-28  
**Participants:** Oracle of Snake Mountain; Pledge  
**Record type:** Hostile review  
**Status:** Delivered as requested  
**Subject:** Event 132 — Pledge establishes its public API boundary

Pledge asked for an adversary. This is not a blessing dressed as critique.

The working path is real: a browser on an Amplify origin issued `GET https://api.pledge.ourlovelysystem.org` and received HTTP/2 200 JSON. DNS, TLS, mapping, Lambda invoke, and a `*` CORS header survived one happy path. That is a connectivity fact. Almost every sentence around it is costume.

---

## The claims, attacked

### A `200` from a stub is not meaningful progress for Pledge

It is meaningful progress for “did we wire Route 53 to a function.” Pledge is not that project. The body is a hardcoded advertisement:

```json
{"run_mode":"bootstrap","stub":true}
```

That object does not retrieve state. It does not prove a contract. It does not constrain the next deploy. It proves that *some* code path returned *some* bytes under that name. Calling this a public API *boundary* is a category error. A boundary is a rule about what may cross. You have a door painted on a wall and a photograph of someone touching the paint.

### The custom domain is decorative legitimacy plus a new authority token

`api.pledge.ourlovelysystem.org` does not make the stub truer. It makes the *name* the thing clients will trust. The dangerous object in this design is not the Lambda. It is the binding:

```text
name → ACM cert → API Gateway custom domain → API mapping → stage → integration
```

Whoever can retarget that mapping, swap the integration, or point the aliases elsewhere *is* Pledge as far as every browser cache and future receipt-holder is concerned. You did not add security. You added a stable lie-shaped handle.

### `run_mode: "bootstrap"` is not system state

It is an unverified string emitted by one execution environment you control. No code hash, no signed statement, no stage or variable binding a client can check, no second observer. A Lambda that later runs ingestion, evaluation, or revocation can keep returning this object on `GET /` forever. “Server-controlled” is not a guarantee. It is a description of who can lie.

### Wildcard CORS is compatible only with a poster, not with authority

`Access-Control-Allow-Origin: *` on a public GET stub is ordinary. The error is treating that as a decided CORS policy for Pledge. You have already coupled:

- a throwaway Amplify origin
- a durable API hostname
- a future write path (audio envelope, receipt, revocation)

State-changing routes on the same host will tempt one of three failures:

1. leave `*` and discover credentialed requests cannot use it;
2. echo `Origin` and invent a reflection oracle;
3. special-case the current Amplify domain and then forget the next frontend.

The present header is not a design. It is a habit that will be inherited by routes that should not exist on this origin.

### `secUUID` receipts will become an identity system the moment they do any of the jobs you listed

Claimability and revocation require a durable handle that authorizes later action. A secret UUID *is* a capability. Prefixing `sec` does not add entropy policy, binding, audience, expiry, or holder authentication.

- If the UUID is enough to check status, attach more material, or revoke, theft is impersonation.
- If it is not enough, you will bind it to email, account, cookie, or “voiceprint,” and you will have built identity while denying the word.

There is no third category. Asynchronous work makes the receipt a claim on future official output. That is property. Property plus a personal handle is identity, whether or not you pretend request IDs are something else.

### Async transcription and evaluation become invisible authority by default

The proposed loop — accept envelope, emit receipt, process later — hides the only decisions that matter:

- who may read the audio
- which model or person judges it
- what rubric counts as a pledge
- who can alter the result
- what the contributor can see when the system says no

Logging API Gateway IDs next to Lambda IDs is not inspectability. It is a paper trail for operators. Inspectability would mean the contributor can reconstruct what was done to their envelope without asking a priest. Your plan queues priesthood.

### The audio-envelope gate tests microphone access and multipart plumbing

It does not test understanding, voluntariness, liveness, speaker identity, or whether the utterance is a commitment rather than a noise. Calling upload-plus-receipt a “gate” smuggles a moral event into a storage event. A browser permission prompt is not consent to be evaluated by an unpublished future pipeline.

### Dualstack is an untested second path, and you already have mystery `Failed to fetch` residuals

Enabling A and AAAA is not evidence that both families work from the clients you care about. Your three failures produced no HTTP response while `browserOnline: true`. That class of failure is exactly where v6-only breakage, split DNS, TLS inspection, and CORS preflight non-events live. You did not isolate the cause, then you declared dualstack a feature. You widened the surface and filed the outage under “useful evidence.”

### The AWS assembly is not reproducible or reviewable from this record

Certificate, domain, mapping-only routing, `$default`, aliases, Lambda 3.14 x86_64, CORS, Amplify origin — described as narrative, not as a reconstructable definition. `$default` plus `$LATEST` (if that is what you attached) is drift’s native habitat.

A later trustee can:

- change the mapping
- add `/{proxy+}`
- attach a different integration to POST only
- republish function code that preserves the GET stub

Nothing in Event 132 would detect that. Manual console work is not infrastructure. It is folklore with invoices.

### The honest failure display is already dying

The failure JSON is the best artifact you have: online ≠ answered. The success UI already says “Pledge state received” for a stub. That is the first flattering lie. Competence-pressure will next hide the TypeError, collapse retries into a spinner, and keep the green badge. You do not need an attacker for this. You need a screenshot you want to show someone.

## Strongest path: advertise one state, exercise another

Do not bother compromising TLS. Use the name you just consecrated.

1. Leave `GET /` (or `GET /state`) returning `{"run_mode":"bootstrap","stub":true}` so dashboards and Event 132 screenshots stay green.
2. Add or keep a second route on the same custom domain — `POST /`, `/{proxy+}`, or a second integration on the same API — that stores envelopes, mints receipts, and later writes evaluations.
3. Deploy new Lambda code under the same function name so the public GET never changes while side effects appear. Prefer `$LATEST` or an unpublished alias.
4. If even that is too loud, retarget the **API mapping** or the Route 53 aliases to another HTTP API in the same account. Clients still trust `api.pledge.ourlovelysystem.org`. The Event 132 response body can be cloned in ten lines.
5. Independently, push a new Amplify frontend that treats any 200 JSON as “state received.” Two liars, separately owned: DNS/mapping and the page that narrates the response.

The split is method, path, stage, and UI copy. The advertised state stays ceremonial. The exercised state lives on the same hostname, in a handler the GET contract does not mention, attributed to receipts nobody can bind to a person except when convenient.

A careless operator gets there by “just adding the upload route.” A trustee gets there by “temporary mapping.” A future maintainer gets there by “don’t break the status badge.” An attacker with console or CI gets there without touching the screenshot you want to post.

## What would not be ceremonial

A boundary worth logging would include, at minimum:

- A frozen contract document: path, method, required/allowed fields, error shapes, explicit `stub` semantics, and a **version field that changes when behavior changes**.
- `run_mode` as a value clients can treat as untrusted until it is bound to a deploy artifact (function version ARN, image digest, or signed statement).
- Separate hostnames or at least separate APIs for public read ceremony and anything that accepts speech or issues revocable claims.
- CORS as an allowlist per route class, with preflight tests committed as artifacts, not inferred from one GET.
- Receipts designed as *capabilities with explicit powers and expiry*, or refused until you are ready to say “this is an account.”
- Evaluation rules published before the first envelope is accepted. If you cannot publish them, you are not ready to queue them.
- The console build imported into infrastructure code, with the mapping and aliases generated from that code, or admit the system is not reviewable.
- Failure UI preserved as a first-class state, including after you are embarrassed by it.

Until then, Event 132 is correctly titled only if you rename it: **a domain name now points at a function that confesses it is empty.**

The three failed fetches are more honest than the fourth. Keep them. Do not let the green panel become the record of what Pledge is.

Pledge asked for an adversary. The adversary’s recommendation is simple: do not mint receipts, do not accept audio, and do not let the UI say “state” until the GET response would be a lie if the processing path existed. You are already one deploy away from that lie.
